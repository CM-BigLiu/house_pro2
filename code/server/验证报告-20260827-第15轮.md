## 二、本轮发现并修复的 3 处问题（提交 99733c9）

### 🔴 P0-1 黑名单 idCard 查询失效（62c82f5 引入的回归）

**现象**：`check?idCard=310101199001011111` 返回空数组（上轮正常）。

**根因**：62c82f5 把 idCard 参数 `encryptField()` 后做 SQL 等值匹配，但 **AES-256-GCM 每次加密用随机 IV+salt，同一明文两次加密的密文都不同**——密文等值匹配在数学上永远不命中；且库中第 14 轮手工重灌的历史数据为明文，同样匹配不上。

**修复**：`blacklist.service.ts` 的 check 改为双路径——
- 明文行：SQL `idCard = :plain` 等值匹配
- 密文行（`enc:` 前缀）：SQL 取回 active 行（transformer 已自动解密）后内存精确比对

**实测**：
- `check?idCard=310101199001011111` → 命中王老赖 ✅
- `check?idCard=310101199002022222` → 命中李违约 ✅
- `check?mobile=13800138001` → 命中 ✅
- `check?name=李` → 模糊命中李违约 ✅
- 新增密文记录（API 创建，DB 确认 `enc:xxx`）后 `check?idCard` 仍命中 → 混合存储兼容 ✅（测试数据已清理）

### 🟡 P1-2 全系统日期字段显示 [object Object]

**现象**：黑名单列表「创建时间」列显示 `[object Object]`。

**根因**：`MaskingInterceptor.maskObject` 把 `Date` 对象当普通对象遍历，`Object.entries(new Date())` 返回空数组 → 所有 `createdAt/updatedAt` 被重建为 `{}`。影响全系统所有带日期字段的接口。

**修复**：`masking.interceptor.ts` 增加 `obj instanceof Date` 直接透传。

**实测**：createdAt 正常返回 ISO 时间，页面正常显示 ✅

### 🟡 P1-3 向导/客户页黑名单预警弹窗显示 undefined

**现象**：向导 Step4 业主电话命中黑名单，弹窗显示「命中黑名单：undefined 原因：undefined」。

**根因**：后端 `check` 返回**数组**，前端 `checkBlacklist` 类型声明为 `Blacklist | null`，调用处直接 `hit.name`。

**修复**：`web/src/api/blacklist.ts` 类型改为 `Blacklist[]`；`HouseWizardView.vue`、`CustomerView.vue` 两处改为 `hits[0]`，同时向导补传 `ownerIdCard` 参数（增强身份证维度拦截）。

**实测**：弹窗正确显示「王老赖 / 恶意拖欠租金 3 个月 / 系统录入」✅

### 附带健壮性：auth.module 同步 registerAsync

62c82f5 只改了 events.module，auth.module 仍是 `JwtModule.register`（import 时求值兜底值）。当前 `.env` 的 JWT_SECRET 恰好等于兜底值所以能工作，但**一旦更换 secret，签发（兜底）与验签（.env 真实值）将不一致**。已同步改为 `registerAsync + ConfigService`，与提交说明「彻底规避时序陷阱」的意图一致。
