## 二、Bug 清单（按优先级）

### 🔴 P0 — 核心功能断裂

#### BUG-1 前后端 refresh 契约不一致：刷新成功后 refreshToken 被清空，2h 后无法续期

- **状态**：✅ **已修复**（2026-09-08，采用方案 A）
- **严重级别**：P0（破坏 auth-token-refresh 核心目标「静默续期」）
- **现象**：用户登录后 access token 2h 过期，前端 401 → 调 `POST /auth/refresh` 刷新成功，但本地 `refreshToken` 被覆盖为 `undefined` 并清除；下一次 access token 再过期时，前端发现本地无 refreshToken，直接强制跳登录页。用户 7d 内本应静默续期，实际 2h 即被踢出。

- **根因**：前后端接口契约不一致。
  - **后端** `AuthService.refresh` 仅返回 `{ accessToken }`（refresh token 不轮换，故不回传）：
    - `code/server/src/modules/auth/auth.service.ts:146` → `return { accessToken };`
    - `code/server/src/modules/auth/auth.controller.ts:41-44` 直接透传该结果
  - **前端** `doRefresh` 期望返回 `{ accessToken, refreshToken }` 并用返回值覆盖本地存储：
    - `code/web/src/api/auth.ts:19-22` → `interface RefreshResult { accessToken; refreshToken }`
    - `code/web/src/utils/request.ts:25` → `userStore.setTokens(res.accessToken, res.refreshToken)`
    - `code/web/src/stores/user.ts:28-41` → `setTokens(access, refresh)` 中 `refresh` 为 `undefined` 时执行 `localStorage.removeItem('house_refresh_token')`，**清空 refresh token**

- **为何测试未暴露**：后端单测只断言后端返回 `accessToken`；前端单测 mock 的 `refreshTokenApi` 按前端期望返回了 `{ accessToken, refreshToken }`，未走真实后端，掩盖了契约断裂。属于典型「mock 全绿、真实联调必挂」。

- **涉及文件**：
  - `code/server/src/modules/auth/auth.service.ts`
  - `code/web/src/utils/request.ts`
  - `code/web/src/api/auth.ts`
  - `code/web/src/stores/user.ts`

- **修复建议**（二选一，推荐 A）：
  - **A（后端，改动最小）**：`AuthService.refresh` 返回时把传入的 refreshToken 原样带回：`return { accessToken, refreshToken }`（不轮换，原样返回）。
  - **B（前端）**：`doRefresh` 成功后只更新 accessToken、保留原 refreshToken（如 `setTokens(res.accessToken, userStore.refreshToken)`）。
  - 补一条跨前后端的集成/契约测试（真实后端 mock-server 或 e2e），断言 refresh 后前端本地 refreshToken 仍在。

- **修复记录**：
  - `code/server/src/modules/auth/auth.service.ts:146` → `return { accessToken, refreshToken }`（refreshToken 原样带回，不轮换）。
  - `code/server/src/modules/auth/auth.service.spec.ts` → 单测新增契约断言 `result.refreshToken === REFRESH_PLAIN`。
  - `code/server/src/int/auth-token-refresh.int.spec.ts` → FULL 全链路新增断言：refresh 响应带回原 refreshToken，且跨多次刷新仍可续期（模拟跨 2h 再刷新）。
  - 验证：后端 `npm test` 3 套件 / 21 用例全绿；前端 `npm test` 5 用例全绿（前端无需改动，本就符合契约）。

### 🟠 P1 — 重要

#### BUG-2 ESLint 配置缺失（前后端均缺）

- **状态**：✅ **已修复**（2026-09-08）
- **现象**：`npm run lint` 直接报 `ESLint couldn't find a configuration file`。
- **根因**：`code/server` 与 `code/web` 均无 `.eslintrc*` 或 `eslint.config.*` 配置文件。
- **影响**：静态检查不可用，CI 中 lint 步骤会挂；代码风格与潜在错误无法被拦截。
- **涉及文件**：`code/server/`、`code/web/`（缺配置文件）
- **修复建议**：分别为前后端补齐 ESLint 配置（如 NestJS 用 `@typescript-eslint` + `eslint-config-prettier`；Vue 用 `eslint-plugin-vue`），并同步 `package.json` 的 lint 脚本。
- **修复记录**：
  - `code/server/.eslintrc.js`：NestJS 标准配置（`plugin:@typescript-eslint/recommended`），关闭 `no-explicit-any` 等对存量代码不友好的规则，`no-unused-vars` 降为 warn。`npm run lint` → 0 errors / 24 warnings，EXIT 0。
  - `code/web/.eslintrc.js`：`eslint:recommended` + `plugin:@typescript-eslint/recommended` + `plugin:vue/vue3-recommended`，关闭纯格式化类 vue 规则（`max-attributes-per-line` 等）避免存量噪音。`npm run lint` → 0 errors / 4 warnings，EXIT 0。

#### BUG-4 `.env` / `.env.example` 缺少 auth-token-refresh 新配置项

- **状态**：✅ **已修复**（2026-09-08）
- **现象**：本变更（auth-token-refresh）引入的新配置项均未写入 `.env` / `.env.example`，生产部署会漏配。
- **缺失项**：`JWT_ACCESS_EXPIRES_IN`（2h）、`JWT_REFRESH_EXPIRES_IN`（7d）、`JWT_REFRESH_SECRET`（独立密钥）、`FIELD_ENCRYPTION_KEY`（敏感字段加密密钥）。
- **当前兜底**：代码里均有硬编码默认值（如 `auth.service.ts:70-72` 用 `'house_pro_jwt_refresh_secret_change_in_production'` 兜底）。
- **风险**：`JWT_REFRESH_SECRET` 兜底值可预测，生产若忘配，攻击者可伪造 refresh token → 账户劫持。
- **涉及文件**：`code/server/.env`、`code/server/.env.example`
- **修复建议**：将 4 个新配置项写入 `.env.example`（值留空或占位），并在部署文档标注「生产必填，尤其 JWT_REFRESH_SECRET 与 FIELD_ENCRYPTION_KEY」。
- **修复记录**：
  - `.env.example`：新增 `JWT_ACCESS_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN` / `JWT_REFRESH_SECRET`（占位值 + 生产必填注释）/ `FIELD_ENCRYPTION_KEY`（留空 + 生成方式注释）。
  - `.env`：新增同 4 项，其中 `FIELD_ENCRYPTION_KEY` 填入开发用 32 字节 base64 值（消除 `[Encryption] FIELD_ENCRYPTION_KEY not set` 告警）。

### 🟡 P2 — 一般

#### BUG-5 FIELD_ENCRYPTION_KEY 未设置，加密走开发兜底密钥

- **状态**：✅ **已修复**（2026-09-08）
- **现象**：测试日志出现 `console.warn('[Encryption] FIELD_ENCRYPTION_KEY not set, using fallback key for development only')`。
- **根因**：`.env` 未配置 `FIELD_ENCRYPTION_KEY`，`crypto.util.ts` 回退到硬编码开发密钥。
- **影响**：生产若沿用，身份证/手机号等敏感字段的 AES 加密密钥可预测，脱敏保护形同虚设。
- **涉及文件**：`code/server/src/common/utils/crypto.util.ts`、`code/server/.env`
- **修复建议**：生产强制注入随机 `FIELD_ENCRYPTION_KEY`（32 字节 base64），并在代码中生产环境（`NODE_ENV=production`）缺失时直接报错而非兜底。
- **修复记录**：
  - 生产报错逻辑已存在（`crypto.util.ts:12-14` 生产环境缺失直接 throw）。
  - `.env` 已补开发用 `FIELD_ENCRYPTION_KEY`（BUG-4 一并处理）。
  - 新增 `code/server/test/setup-env.ts`，在 jest `setupFiles` 注入测试专用密钥（单测 + e2e 两处 jest 配置均已接入），消除测试日志 warn 噪音。后端 `npm test` / `npm run test:e2e` 均无 `[Encryption]` 告警。

#### BUG-6 前端测试 jsdom 导航噪音（redirectToLogin 未 mock）

- **状态**：✅ **已修复**（2026-09-08）
- **现象**：前端单测输出 `Error: Not implemented: navigation (except hash changes)`，源于 `redirectToLogin` 中 `window.location.href = '/login'`。
- **根因**：`request.ts:35-39` 的 `redirectToLogin` 在 jsdom 环境触发 `location.href` 赋值，jsdom 不支持导航。
- **影响**：测试虽通过但输出脏噪音；`redirectToLogin` 的跳转副作用未被断言，存在回归盲区。
- **涉及文件**：`code/web/src/utils/request.ts`、`code/web/tests/auth-token-refresh.spec.ts`
- **修复建议**：测试中 mock `window.location`，并断言「refresh 失败后确实调用 redirectToLogin」。
- **修复记录**：
  - `code/web/tests/auth-token-refresh.spec.ts` 拦截器 describe 的 `beforeEach` 中用 `Object.defineProperty` 替换 `window.location` 为可写 mock（`{ href: '', pathname: '/' }`）。
  - 「refresh 失败 → 清空登录态」用例新增断言 `expect((window.location as any).href).toBe('/login')`，覆盖 redirectToLogin 跳转副作用。
  - 前端 `npm test` 5/5 PASS，无 `Not implemented: navigation` 噪音。
